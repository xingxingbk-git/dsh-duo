## 2. 已确认正确的内容

- `dsh.bundle.patch`、Cordis patch 中按包名插入插件，以及 `dsh.client.platform: web` 配合 `exports["./client"]`，符合[官方打包文档](https://deepseek-harness.github.io/deepseek-harness/en/develop/basic/publish)和[Client Modules 文档](https://deepseek-harness.github.io/deepseek-harness/en/reference/subsystems/client-modules)。安装版桌面 Host 使用本地 Web server 和同一客户端模块加载器，静态确认接受 `platform: web`；本项目的实际桌面装载仍需验证。
- 两端导出 `name`、`apply`，Client 声明 `slots`/`layout` 服务依赖，方向正确。目前两端 `apply` 都是空函数。
- 复用外层布局、通过 `main` 注册独立 Chat 面板、Chat 与 Harness 数据隔离、停用后恢复原行为，都是合理目标。
- `sidebar.workspaces` 是聊天历史区的候选位置，进入 CHAT 才注册替代项、退出时 dispose 的方向合理。注册须使用声明感知的 `slots.inject` 生命周期，参见[官方 Slots 文档](https://deepseek-harness.github.io/deepseek-harness/en/reference/subsystems/slots)。
- 现有需求对网页同步、匿名迁移保持“待验证”，这是必要的能力边界，不是框架缺陷。

## 3. 需要修正的架构判断

### 品牌名槽不是已确认的交互区域（优先解决）

`docs/architecture.md` 第 21、27、34 行把 `sidebar.brand.name` 当作切换按钮位置。目前安装版：

- `ui-sidebar/lib/client.js` 309–318：品牌名只在展开时渲染，位于 `aria-hidden="true"` 的 `brandIdentity` 内。
- 同文件 334–348：macOS 桌面外层为 `span`；普通 Web/Windows 外层是会触发 `startSession()` 的 `button`。

因此，放两个交互按钮进去会落在对辅助技术隐藏的祖先内；Web/Windows 还存在嵌套按钮和错误触发新建 Harness 会话的风险。子节点增加 ARIA 属性或阻止点击冒泡，不能完整解决这个契约问题。折叠后品牌名不渲染，也不能满足“切换器始终可达”。对应版本[官方 SidebarRoot.tsx 第 223 行](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/packages/client/ui-sidebar/src/client/SidebarRoot.tsx#L223)可直接复核祖先隐藏，241–252 行可复核外层点击行为。

原视觉目标可以保留，但这个实现位置必须先解决官方交互契约。可调研官方新增/开放品牌操作槽，或完整侧栏替代方案；后者需要额外核查子槽 ownership、内置控件和恢复，不属于当前已确认的窄槽实现。`sidebar.footer.action` 是现有的可交互 list 槽，可用来做最小可行性验证，但改变了目标位置，不能称为最终需求已实现。

### 替换历史区不会替换所有 Harness 操作

安装版 `ui-sidebar/lib/client.js` 356–377 的“新建会话”按钮属于 Sidebar shell，392–399 才是 `sidebar.workspaces`；品牌点击和快捷键也有独立路径。

只替换 workspace 区后，这些操作仍可能创建 Harness Session。CHAT 的新建、快捷键、折叠入口、面板导航必须一起审计，不能把“换历史列表”当作“整个侧栏已进入 CHAT”。未知 shortcut/导航接口仍须先用 Inspect 发现。

### 右栏优先利用主面板切换，避免主动关闭

安装版 `ui-sidebar-right/lib/client.js` 5851–5881 将 Session 右栏的可见性绑定到 `activePanelId === null`，9060–9063 按同一条件选择显示的 Session。进入独立 Chat `main` 面板可自然隐藏 Harness 右栏，并保留其 Session 子树。这是静态证据，尚未做插件往返操作验证。

因此，`architecture.md` 第 24 行“Chat 时请求 closeRightbar”的策略应改为先验证原生 panel 导航行为，暂不把 `closeRightbar/openRightbar` 当作模式切换操作。它们控制布局呈现，不能等同于保存和恢复所有标签状态。最新版[官方 Layout 文档](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/client/ui-layout/README.md)也说明右栏与 Conversation 可见性相关，但其内部描述与 rc.2 产物存在差异，不能混用。

`layout.panelInfo` 的只读 `getSnapshot/subscribe` 和 `usePanelInfo` 已在安装产物确认。返回 HARNESS 应恢复此前 `activePanelId`；此前可能是 Plugins 等全局面板，不能一律 `selectPanel(null)`。旧面板若已卸载，应有默认 Conversation 的回退处理。标签、宽度、全屏、浮动面板和焦点恢复都仍需实测。

## 6. 建议补充的验收标准与开发顺序

以下为审查建议，未替用户决定首期采用本地聊天或 API 替代网页同步：

1. 先解决品牌切换器的交互契约和折叠时入口，再做位置与白底选中态验证；确认没有嵌套按钮、辅助技术隐藏或窗口拖动冲突。
2. CHAT 的新建按钮、品牌点击、快捷键和全局面板操作都不能意外创建/切换 Harness Session。
3. CHAT 发送走已确认的普通聊天数据路径，不因复用 Agent 会话而继续调用编码工具、命令或文件操作。仅隐藏工具 UI 不能满足 Chat 模式的行为需求。
4. 往返切换保留原 Session、原主面板、右栏标签/全屏/宽度/浮窗、草稿与阅读位置；生成中的回答有明确继续/停止策略，模式切换本身不静默取消。
5. Chat 草稿、流式请求和历史存储的生命周期独立于 React 面板挂载。持久注册 main entry 不等于选中其他 panel 后组件状态必然保留。
6. 插件在 CHAT 时禁用、卸载、失败或重载也必须能退出 Chat 并恢复内置界面；未知的恢复能力继续标“待验证”。
7. 官网同步和匿名迁移继续作为独立能力审计；若同步是首期必需，先解决官方接入路径再接真实数据。Mock 只用于界面验证，不能当聊天能力验收。

推荐首个可验证阶段：确定 0.2.0-rc.2 兼容依赖与构建 → 官方 Slot/owner/shortcut Inspect → 可达的模式入口与 mock 主面板 → 原生右栏隐藏和往返恢复 → 禁用/卸载恢复。通过后再选择真实聊天数据源。
